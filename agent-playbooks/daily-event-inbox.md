# Daily Charlotte event inbox

The owner explicitly authorized this recurring workflow: find Charlotte events with images, have Astra check them, and send accepted events to the inbox for the owner to approve. This grants standing permission to submit pending entries, not to approve or publish them. For this workflow, that authorization supersedes the owner-only submission and shell restrictions in event-scout.md. All other source and untrusted-content safeguards still apply.

## Each run

1. Work in `C:/Users/sahil/communityplansapp`. Read `event-scout.md`, `sources.md`, the current inbox validator, and this playbook. Use the current date in America/New_York; find events in the next 30 days. Use inexpensive scouting agents (gpt-6-luna) and reserve gpt-6-astra for judging. Do not silently substitute a cheaper judge if Astra is unavailable.
2. Read existing upcoming app events and prior agent submissions, including pending and rejected entries, using available authenticated Supabase tooling. Avoid duplicate title/venue/date occurrences across sources, not just identical URLs. If the existing inventory cannot be checked, stop before submitting. Never approve, overwrite, or delete existing records. Flag material changes to previously submitted events for the owner instead of reposting them.
3. Browse public venue and organizer websites from sources.md and relevant public search results. No logged-in social accounts, restricted pages, CAPTCHA bypass, or Eventbrite/Meetup crawling. At most about 60 pages per run, sequentially; aim for up to 20 new, well-supported events. Fewer or zero is fine. Never invent dates, times, venues, prices, or images. Distinguish event starts from doors and ticket-sale times and use correct Eastern offsets.
4. For each candidate, collect an official HTTPS event image URL and download a local review copy. Confirm the URL serves an image and associate it with the exact event or its named performer/recurring series. Reject unrelated venue logos, generic unrelated photographs, and posters for conflicting dates or venues. Keep provenance outside the inbox JSON.
5. Save a dated batch under `marketing/event-inbox/YYYY-MM-DD/`, with candidates, original review images, and a source manifest. Preserve previous runs and the existing root events.json. Spawn a gpt-6-astra judge with a compact brief. It must independently check the primary event evidence and inspect actual image pixels for every candidate. Record an explicit per-event accepted/revise/rejected result. An undated official series image or an officially assigned performer photo is acceptable when clearly documented. If Astra cannot complete review, retain drafts and do not submit unreviewed items.
6. Correct supported findings and have Astra recheck changed candidates. Make at most two review rounds; omit unresolved candidates. Write only accepted entries to the dated `events.json`. Use only fields accepted by `supabase/functions/agent-inbox/validate.ts`, including image_url. Run that actual validator, check uniqueness and request limits, and verify each final image URL matches the judged manifest.
7. Submit the accepted batch to `https://lvgmelaavgmyjjdggzop.supabase.co/functions/v1/agent-inbox`. Read YARD_AGENT_SECRET securely from the process or Windows user environment. Never print, persist, expose in command arguments, or send the secret to any other destination. Do not log authorization headers or raw credential-bearing errors. If unavailable, stop and report the setup issue; do not rotate credentials or substitute a service-role insert.
8. Save the sanitized response and verify accepted rows are pending with the expected image URLs. Report received, inserted, duplicate, and rejected counts. Investigate failures without publishing or weakening validation. An ambiguous request outcome must be checked against stored fingerprints before retrying; the endpoint's deduplication makes a same-batch retry safe.

No automatic approval, curated-event creation, publishing, deployment, database migration, paid API purchase, or account changes are authorized by this daily workflow. The owner reviews the inbox and decides what reaches the app.
